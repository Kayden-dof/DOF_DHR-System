# DOF DHR 지원 시스템

의료기기 GMP 제조소용 제조기록 **지원** 도구. `CLAUDE.md` 전 범위(M0~M4) 구현.

**정본은 서명된 종이다.** 시스템은 종이를 발행하고 입력된 기록을 집계한다.
판정하지 않고, 차단하지 않고(S01~S05 다섯 개 제외), 전자서명을 받지 않는다.

| | 범위 | 상태 |
|---|---|---|
| M0 | 사용자 · 권한 · 감사추적 · 채번 규칙 | 완료 |
| M1 | 기준정보 · 자재 로트 · 작업지시 · 자재 투입 | 완료 |
| M2 | 제품 로트 · 공정 기록 · 인쇄 · 잠금 | 완료 |
| M3 | 재고 · 발주 · 용액 제조 · 조회 | 완료 |
| M4 | 멸균 · 출하 승인 · 출고 · 원가 집계 | 완료 |

조작 모드는 **로그인 이후로 갈린다.** 관리자 역할이면 관리 화면(`/`), 작업자면
현장 화면(`/work`)으로 넘어간다. 현장은 장갑 낀 손과 패드를 전제하므로 키보드를
쓰지 않고 조작 대상이 56px 아래로 내려가지 않는다.

## 실행

```bash
npm install
npm run dev
```

PostgreSQL 18을 띄우고(첫 실행이면 초기화 · 마이그레이션 · 초기 관리자 생성) 이어서
`http://localhost:3100`에 앱을 붙인다. 관리자 권한도 사전 설치도 필요 없다
`embedded-postgres`가 공식 바이너리를 `node_modules`에 들고 있다.

초기 관리자는 로그인 `1001` / 비밀번호 `135790`. **로컬 개발용이며 운영에 쓰지 말 것.**
데이터를 지우려면 `npm run dev:reset`.

시험은 셋으로 나뉜다. 보는 것이 서로 다르다.

```bash
npm test              # 규칙 · 구조 · 채번 · 계보 · 검토 지원 122건 (PGlite, 서버 불필요)
npm run test:pg       # 위 122건 + 동시성 6건 (실제 PostgreSQL을 띄웠다 내린다)
npm run smoke         # 실자료가 든 상태에서 화면 30개가 그려지는지 (앱이 떠 있어야 함)
npm run test:print    # 인쇄 충실성 107항목 (§8.2 · 앱과 실자료가 있어야 함)
```

`npm test`가 **DB 계층이 규칙을 지키는지**를 본다. `smoke`가 **화면이 그려지는지**를
보고, `test:print`가 **그려진 종이가 자료와 같은지**를 본다. 종이가 정본이므로 셋째가
사양이 말하는 "가장 중요한 검증"이다 (§8.2).

동시 채번 조건은 `SESSIONS`, `PER_SESSION`으로 바꾼다(기본 2세션 × 50회).

> 시험은 데이터를 남기고 지우지 않는다(삭제 자체가 없다). 실운영 DB를 가리키지 말 것.

**initdb 인코딩 주의.** Windows 사용자명이 한글이면 initdb의 post-bootstrap이 CP949
바이트를 UTF8 클러스터에 밀어넣다 죽는다(`invalid byte sequence for encoding "UTF8"`).
`scripts/dev.mjs`와 `test/pg.mjs`는 클러스터를 `SQL_ASCII`로 만들고 시험 · 개발 DB만
`template0`에서 UTF8로 뽑아 우회한다. 스키마가 도는 DB는 UTF8이라 검증 값은 유효하다.

## 화면

### 관리 화면 (키보드 · 마우스)

| | 하는 일 |
|---|---|
| **현황** | 지금 막혀 있는 것과 진행 중인 것. 이상이 없으면 아무것도 표시하지 않는다 |
| **생산** | 작업지시 발행(소요량 미리보기), 배치 진행, 재단 분할, 인쇄 |
| **자재** | 입고 등록(S01 · S02), 발주, 재고, 반납 · 폐기 · 용액 제조 |
| **출하** | 멸균 위탁 발송 · 회수, 서면 출하 승인 전사, 출고 |
| **조회** | 로트번호 하나로 정추적 · 역추적. 제품 원가와 자재 지출 |
| **설정** | 채번 규칙 · 품목 · 공급자 · 제품표준서 · 사용자 · 감사추적 |

### 현장 화면 (패드 · 장갑)

| | 하는 일 |
|---|---|
| **배치 목록** | 지금 손댈 수 있는 배치만 큰 타일로 |
| **공정 기록** | 일차 · 공정을 타일로 고르고, 수량은 숫자 패드, 사유는 정해진 문구에서 고른다 |
| **일차 마감** | 마감하면 기록서가 발행되고 그 묶음이 잠긴다 (S04). 푸는 방법은 없다 |
| **자리 비움 잠금** | 20분 손을 대지 않으면 화면을 덮는다. 로그아웃이 아니라 잠금이라 비밀번호를 다시 누르면 하던 자리로 돌아온다 |

남이 이미 기록한 공정은 회색 띠와 이름으로 표시한다. 기록지는 작업자별이라
내 화면에는 빈칸으로 보이는데, 그대로 두면 같은 공정을 두 번 한다.

### 인쇄 (§7)

작업지시서 · 제조기록서 · 라벨요청서 · 편철 표지 · 자재 라벨 · 출하 승인 요청서.
모든 인쇄물에 인쇄 일시 · 인쇄자 · 인쇄 회차 · 자료 식별자 · 쪽 번호가 들어간다.

**같은 기록의 종이가 두 장 도는 것이 이 시스템에서 가장 위험한 상태다.** 종이만
봐서는 어느 것이 최신인지 알 수 없고, 잘못된 쪽에 서명이 들어가면 되돌릴 방법이
없다. 그래서 셋을 둔다.

- **재발행 표시** - 2회차부터 종이에 사선으로 "재발행 n회차" 가 찍힌다
- **회수 기록** - 앞 종이를 거둬들인 사실과 사유를 남긴다. 되돌릴 수 없다
- **자료 식별자 조회** (`/trace/verify`) - 손에 든 종이의 12자리를 넣으면 그 종이가
  무엇이고 **그 뒤에 다시 뽑은 회차가 있는지**를 답한다. 바코드를 읽어도 같다

제조기록서는 **화면을 여는 것만으로** 그 묶음이 잠긴다 (S04). 순번과 자료 식별자가
붙은 종이가 그 순간 존재하게 되고, 실제로 인쇄했는지는 브라우저 밖의 일이라 알 수
없기 때문이다. 잠금 해제는 없으므로 첫 발행 앞에 확인 단계를 둔다.

### 검토 지원 (§8.5)

배치 화면 맨 위에서 **산술로 어긋나는 것만** 짚는다. 시각 역전, 반납이 불출보다 큼,
장입 구간과 다른 시약 기입량, 사유로 넘어간 자재, 지정 원재료와 다른 투입 로트,
예정과 다른 재단 수량.

사실만 적고 판정 문구를 쓰지 않는다. **이상이 없으면 아무것도 표시하지 않는다.**
`"이상 없음"` 을 내보내지 않는 이유는 그 문구가 뜨는 순간 검토자가 그것을 믿고
넘어가는데, 시스템이 잡을 수 있는 항목보다 잡을 수 없는 항목이 훨씬 많기 때문이다.
표시가 있어도 인쇄와 진행을 막지 않는다. 차단은 S01~S05 뿐이다.

### 계정 워터마크

화면 전체에 로그인 계정 · 사번 · 본 시각이 아주 옅게 깔린다. 인쇄물에는 나오지
않는다. **캡처를 막지 않고, 막는 척하지도 않는다** - `Win+Shift+S` 도 휴대폰
카메라도 웹이 관여할 경로가 아니다. 찍힌 그림에 누가 언제 봤는지가 함께 남을
뿐이고, 찍는 사람이 그 사실을 안다.

### 화면은 규칙을 판정하지 않는다

차단은 DB 계층에 있다(S01~S05, 채번 불변식, 개발계정 QP 금지). 화면은 예외를 받아
**그 문장을 그대로 보여준다.** 응용에서 한 번 더 판정하면 두 곳이 어긋나는 순간
검증이 깨진다. 개발 계정에 품질책임자를 부여하면 화면에 이렇게 뜬다:

> 개발 계정에는 품질책임자 역할을 부여할 수 없습니다

미리보기도 마찬가지다. 화면에서 문자열을 조합하지 않고 `preview_number()`를 거친다
(§10 *"채번 번호를 응용 계층에서 조합"* 금지). 규칙은 등록 후 수정할 수 없으므로
미리보기가 실제 발행과 어긋나면 되돌릴 방법이 없다 - 시험 N-25가 둘의 일치를 고정한다.

### 노출하지 않는 것

- **실제 다음 순번.** §4.10 *"관리 화면에서도 노출하지 않는다."* 미리보기는 표본
  순번 1 · 2회차의 *형식*만 보여준다. `app_role`은 `numbering_counter`에 아무 권한이 없다.
- **비밀번호 해시.** 감사추적의 값 대조에서 `pin_hash`는 `●●●●●●`로 가린다.

## 접속 · 권한 구조

```
브라우저 ──▶ Next 서버 ──▶ withActor(userId, fn)
                              begin
                              set local role app_role     ← S03이 실제로 걸리는 지점
                              set_config('app.user_id', …, true)
                              …질의…
                              commit
```

- **응용은 소유자 권한으로 붙지 않는다.** 트랜잭션마다 `set local role app_role`을
  걸어 구조적으로 강제한다. 소유자로 질의하면 §5의 REVOKE가 통째로 무의미해진다.
- **`app.user_id`는 트랜잭션 로컬**(`set_config`의 3번째 인자 `true`)이다. 커넥션
  풀러가 세션을 재사용하므로 세션 GUC로 두면 다음 요청의 감사기록에 남의 id가 찍힌다.
- 화면 접근 제어(어느 역할이 어느 메뉴를 보는가)는 응용 계층 관심사다. DB가 보장하는
  것은 기록 무결성이지 메뉴 가시성이 아니다.

배치 전 확인:

1. 마이그레이션은 소유자로, 응용은 `app_role`이 부여된 계정으로 접속한다.
   ```sql
   create role dhr_app login password '...';
   grant app_role to dhr_app;
   ```
2. `SESSION_SECRET`(32자 이상)과 `DATABASE_URL`을 환경변수로 준다.
3. **채번 규칙을 등록한다.** 시스템은 채번 *기구*만 제공하고 규칙은 비어 있다.
   규칙 없이 채번을 부르면 예외가 난다. 현황 화면이 미등록 대상을 경고한다.
4. **제품표준서를 등록하고 서면과 대조 확인한다.** 확인하지 않은 개정으로는
   작업지시를 발행할 수 없다.

> **M1이 끝나기 전에 실제 로트를 등록하지 않는다.** 계보는 소급이 안 된다.

## 배포

- **DB** - Supabase `pqtetzyaifhixaoesthp` (ap-northeast-2, PostgreSQL 17.6)
- **앱** - Vercel `dof5/dof-dhr-system` → https://dof-dhr-system.vercel.app

```bash
npm run deploy:db      # 마이그레이션 + 온전성 확인 + 초기 관리자
```

`.env.deploy`(커밋 안 됨)의 `MIGRATION_DATABASE_URL`을 쓴다. 스키마 적용 후
표·함수·`app_role`·API 노출 0건을 확인하고, **`set local role app_role`로 응용
경로를 실제로 밟아 본 뒤** 계정이 없으면 초기 관리자를 만든다.

Vercel 환경변수 두 개가 필요하다. **바꾼 뒤에는 재배포해야 반영된다.**

| 이름 | 값 |
|---|---|
| `DATABASE_URL` | Transaction pooler(6543) URI. `.env.deploy`의 같은 이름 값과 동일하다 |
| `SESSION_SECRET` | 32자 이상. 바뀌면 로그인된 세션이 전부 끊긴다 |
| `CRON_SECRET` | 선택. 넣으면 `/api/daily` 가 `Bearer` 헤더를 확인한다 |

**DB를 먼저 올리고 코드를 나중에 올린다.** 순서가 바뀌면 배포된 코드가 아직 없는
함수를 부른다. 실제로 운영 DB가 배포된 앱보다 네 개 뒤처져 생산·조회 화면이
깨진 적이 있다.

### 일 1회 배치

`vercel.json` 의 예약 작업이 매일 06:00 KST(21:00 UTC)에 `/api/daily` 를 부른다.
기한이 지난 자재를 `EXPIRED` 로 표시하고(§6) 오래된 로그인 시도 기록을 지운다.
판정이 아니라 날짜를 지난 것에 지났다고 적는 것뿐이라 §2 의 차단 다섯 개와 무관하다.
실행자가 사람이 아니므로 감사추적에 수행자가 빈 채로 남는데, 그것이 사실이다.

### TLS

Supabase pooler 인증서는 자체 CA(`Supabase Root 2021 CA`)로 서명돼 있어 Node
기본 신뢰 저장소로는 검증되지 않는다. **검증을 끄지 않고** CA를 준다
`lib/supabase-ca.ts`에 PEM을 박아 두었다.

파일이 아니라 모듈인 이유: 서버리스 번들은 Next의 파일 추적에 잡힌 파일만
싣는다. 런타임에 경로를 계산해 읽는 인증서는 함수에 딸려가지 않아 TLS가 조용히
실패한다. 원본은 `db/supabase-ca.crt`이고 `npm run ca:sync`가 옮긴다.

CA는 공개 CA로 검증되는 HTTPS 경로로 받아, DB 핸드셰이크가 제시한 루트와 SHA256
지문이 일치함을 확인하고 저장했다.

### 로컬 시험이 잡지 못하는 것 - 슈퍼유저 함정

로컬 시험(PGlite · embedded-postgres)은 **슈퍼유저**로 돈다. 슈퍼유저는 권한
검사를 통과하므로 역할 멤버십 문제가 드러나지 않는다. 실제로 62건을 전부 통과한
뒤 Supabase에서만 이렇게 터졌다:

```
permission denied to set role "app_role"   (42501)
```

PostgreSQL 16부터 `CREATEROLE` 계정이 역할을 만들면 ADMIN 옵션만 자동으로 붙고
SET 옵션은 붙지 않는다. Supabase의 `postgres`는 슈퍼유저가 아니라 여기 걸린다.
`0001_app_role.sql`이 멤버십을 명시적으로 부여하고, `deploy-db.mjs`가 배포마다
응용 경로를 그대로 밟아 확인한다.

> **Vercel 플랜 주의.** 현재 팀이 Hobby 플랜이다. Hobby는 약관상 비상업적 용도
> 전용이라 사내 GMP 시스템 운영에는 맞지 않는다. 실사용 전에 Pro 전환을 검토할 것.

## 사양과 다르게 구현한 것

`CLAUDE.md`의 코드를 그대로 옮기면 동작하지 않거나 규칙이 새는 지점들이다.
각 항목은 해당 마이그레이션 주석에 근거와 함께 적혀 있다.

### 고치지 않으면 동작하지 않는 것

| # | 위치 | 내용 |
|---|---|---|
| 1 | `trg_audit()` | `record_id`가 `'id'` 컬럼 고정이라 `user_role`(기본키 `(user_id, role)`)에 걸면 NOT NULL 위반으로 INSERT 자체가 막힌다. 트리거 인자로 식별자 컬럼을 받게 했다. 인자 없으면 `'id'`이므로 M1 이후 표는 사양 그대로 붙이면 된다. |
| 2 | `numbering_rule.item_id` | `references item(id)`인데 `item`은 M1 표다. M0에서는 FK 없이 컬럼만 뒀다. M1에서 넣을 `alter table` 한 줄을 `0004` 주석에 적어 뒀다. |
| 3 | `next_number()` | `p_item`이 있으면 패턴에 품목 토큰이 없어도 `item`을 조회한다. 패턴이 실제로 요구할 때만 조회하게 했다. 이게 없으면 §8.1의 "품목별 규칙 우선" 시험을 M0에서 돌릴 수 없다. |

### 새는 것을 막은 것

| # | 위치 | 내용 |
|---|---|---|
| 4 | `next_number()` 시각 | `now()`는 세션 타임존을 탄다. DB가 UTC면 KST 00:00~09:00 채번이 전날 날짜와 전날 `cycle_key`를 받는다. `Asia/Seoul`로 고정했다. |
| 5 | `security definer` | `trg_audit`, `next_number`에 `search_path`를 고정했다. 미고정 시 호출자가 경로를 바꿔 함수를 가로챌 수 있다. |
| 6 | TRUNCATE | `REVOKE DELETE`는 TRUNCATE를 막지 않고 TRUNCATE는 행 트리거도 타지 않는다. 표를 통째로 비우고 감사기록도 남지 않는다. 문장 트리거로 막았다. CASCADE · 다중 표 경로까지 시험한다(S03-10, S03-18). |
| 7 | 소유자 우회 | `REVOKE`는 app_role만 막는다. 소유자 · 슈퍼유저용으로 삭제 차단 트리거를 함께 걸었다. §2의 S03 구현란이 "REVOKE DELETE + **TRIGGER**"인 이유다. |
| 8 | 개발계정 QP | 사양의 `trg_no_dev_qp()`는 `user_role` 쪽만 막는다. QP를 가진 계정을 나중에 `is_developer=true`로 바꾸는 역방향 경로가 열려 있다. `app_user` 쪽에도 같은 불변식을 걸었다. |
| 9 | `audit_log` UPDATE | 고쳐 쓸 수 있는 감사기록은 감사기록이 아니다. 수정을 막았다. |
| 10 | 규칙 불변성 | §4.10 "기존 행을 수정하지 않는다"를 트리거로 강제. `is_active`를 내리는 것만 허용하고 재활성화도 막는다. |
| 11 | 카운터 역행 금지 | §4.10 "순번을 되돌리면 중복이 발생한다"를 트리거로 강제. 앞으로만 간다. 초기 이관용 시작 순번은 INSERT라 걸리지 않는다. |
| 12 | DELETE 감사 | `app_user` · `user_role`은 §5의 REVOKE DELETE 목록에 **없다** - 역할 회수는 정상 작업이다. 그래서 삭제를 막지 않고, 대신 `after delete`도 감사한다. 회수 시점이 남지 않으면 "누가 언제 어떤 권한을 가졌는가"가 비어 버린다. |
| 13 | 순번 승계 | 규칙을 교체하면 `rule_id`가 바뀌어 카운터가 새로 생기고 순번이 1부터 다시 시작한다. 같은 패턴이면 이미 나간 번호가 재발행된다. 아래 절 참조. |

### 판단해서 뺀 것

- **`numbering_counter`는 감사 대상에서 제외했다.** 채번 1건마다 감사행이 붙어
  `audit_log`가 채번 로그로 뒤덮인다. 발행된 번호는 그 번호를 쓴 기록에 이미 남으므로
  추적에 보태는 것이 없다. 무결성은 역행 금지 트리거와 권한 회수로 지킨다(시험 N-26).
- **`app_user`에 DELETE 권한을 주지 않았다.** 계정 정리는 `is_active=false`로 한다.
  `user_role`에는 DELETE를 줬다 - 전보 · 퇴사 처리와 개발계정 전환이 역할 회수를
  전제로 하기 때문이다.

## 순번 승계 (규칙 교체 시 번호 재사용 차단)

`numbering_counter`의 기본키가 `(rule_id, cycle_key)`라, §4.10의 "규칙 변경은 신규 행
추가로 한다"를 따르는 순간 새 카운터가 생겨 순번이 1부터 다시 시작한다. 같은 패턴이면
**이미 나간 번호가 그대로 재발행된다** - §10이 금지하는 번호 재사용이다.

`next_number()`가 새 카운터 행을 만들 때 같은 `(target, item_id, cycle_key)`의 기존
최대값에서 이어받게 했다. `item_id`는 공통 규칙에서 null이므로 `=`가 아니라
`is not distinct from`으로 비교한다.

**함께 막은 경합.** 승계는 구 규칙 카운터의 *커밋된* 최대값을 읽는다. 구 규칙으로 아직
발행 중인 트랜잭션이 있는데 그 사이 규칙을 내려 버리면 같은 번호가 두 번 나간다.
규칙 조회에 `for share`를 걸어 발행 중에는 규칙을 내리지 못하게 했다. 공유 잠금끼리는
충돌하지 않으므로 동시 발행 성능에는 영향이 없고, 규칙 교체만 발행 종료를 기다린다.
시험 C-05 · C-06이 실제 두 세션으로 확인한다.

**승계 범위**

| 경계 | 동작 | 시험 |
|---|---|---|
| 같은 `(target, item, 주기)` | 이어받는다 | N-07, N-24(3세대) |
| 다른 주기 (`cycle_key`) | 이어받지 않는다 | N-21 |
| 다른 품목 | 이어받지 않는다 | N-23 |
| 공통 규칙 (`item_id` null) | 이어받는다 | N-22 |

**남은 구멍 하나 - 주기를 바꿔 교체하면 승계되지 않는다.** `cycle_key`가 달라지기
때문이다. 패턴을 그대로 두고 주기만 바꾸면 충돌한다. 구조로 막으려면 카운터 키를
`(target, item_id, cycle_key)`로 바꿔야 하는데 그건 §4.10의 표 정의를 고치는 일이라
하지 않았다. **대신 규칙 관리 화면이 경고한다** - 주기를 바꾸면 승계가 끊긴다는 안내가
뜨고, 패턴까지 같으면 "이미 발행된 번호가 그대로 다시 나온다"는 강한 경고로 바뀐다.

## 남은 판단 (물어볼 것)

### 1. `{SEQ:n}`의 `n`과 `seq_width`가 어긋날 수 있다

토큰표는 "`{SEQ:n}` 순번 n자리"라고 하는데 사양의 함수는 `seq_width` 컬럼으로 채운다.
`{SEQ:2}` + `seq_width=7`이면 7자리가 나온다(시험 N-09가 이 동작을 고정해 뒀다).
사양 코드대로 뒀다. 규칙 등록 화면은 둘을 함께 보여주고 미리보기로 결과를 확인시킨다.

### 2. 설비번호를 현장에서 넣을 수 없다

`process_record.equipment_id`가 스키마에 있고 제조기록서 비고란에 인쇄되는데 현장
화면에 입력 칸이 없다. **설비를 기록으로 남길지 먼저 정해야 한다.** 남긴다면 공정
시작 화면에 타일로 고르게 하는 것이 맞고(키보드를 쓰지 않는다) 설비 목록이라는
기준정보가 하나 는다. 남기지 않는다면 제조기록서에서 그 칸을 빼야 한다.

늘 비어 있는 칸이 찍힌 GMP 기록지가 둘 중 어느 쪽보다도 나쁘다.

### 3. 사양에 제약이 없어 그대로 둔 것

- `login_code`는 "숫자 문자열"이라고만 되어 있고 형식 제약이 없다. 화면에서 숫자
  입력을 유도하지만 DB 제약은 넣지 않았다.
- QP 계정의 `can_login=false` / `pin_hash is null` 정합성 제약이 없다.
- `numbering_rule.effective_from`은 기록용이다. 규칙 선택은 `is_active`만 본다.
  활성 규칙이 (target, item)당 하나라서 **미래 일자 규칙을 미리 등록해 둘 수 없다.**

셋 다 차단을 늘리는 일이라 §1("차단하지 않는다")과 §12("완화하지 말고 먼저 물어볼 것")에
따라 임의로 넣지 않았다.
